## 怎么验证"自修复"真的生效了

光靠正常的提示词很难稳定触发报错（模型大部分时候写的代码是对的）。
建议这样测试：

**故意引导模型写出会报错的代码**，比如：

```
做一个页面，用 JS 读取一个不存在的 DOM 元素的 innerText 并打印出来
```

模型大概率会写出类似 `document.getElementById('xxx').innerText` 这种代码，
如果 `xxx` 这个 id 不存在，运行时就会抛出
`Cannot read properties of null` 的报错——这正好可以触发我们的监听脚本。

打开浏览器控制台，你应该能看到：
1. 生成完成后，页面报错
2. 状态栏立刻变成"⚠️ 检测到报错，自动修复中...（第 1 次）"
3. 几秒后，页面内容更新，状态变成"✅ 生成完成（经过 1 次自动修复）"

## 关键改动说明

### 1. `injectErrorCatcher.ts` —— 整个功能的入口

不管是首次生成还是修复后的代码，都要经过这个函数处理一遍再传给 iframe。
它做的事情很单纯：找到 `</body>`，在前面插入一段监听脚本。

### 2. 为什么用 `postMessage` 而不是直接读 iframe 内部状态

`sandbox="allow-scripts"` 限制了 iframe 不能访问父页面（反之亦然），
这是浏览器的安全机制。`postMessage` 是专门为跨源/跨上下文通信设计的 API，
是这里唯一可行的通道。

### 3. `useAutoRepair.ts` 里为什么用 `useRef` 存代码和重试次数

`window.addEventListener('message', handleMessage)` 注册的回调函数，
它捕获的是注册那一刻的闭包。如果直接用 `useState` 的值，
拿到的会是组件上一次渲染时的"旧值"，而不是最新代码——
这是 React Hooks 里经典的"闭包陷阱"。用 `useRef` 存一份始终最新的值，
就能绕开这个问题。

### 4. 重试上限为什么设在前端而不是后端

因为"是否报错"这件事只有浏览器（iframe）知道，后端根本不知道
自己生成的代码有没有问题。所以整个重试计数器必须活在前端。

## 下一步（自然延伸，不是今天的任务）

现在的修复是"报错了才修"，是被动的。更进一步可以做**语法预检**——
在把代码传给 iframe 之前，先用一个轻量 JS 解析器（比如 acorn）
静态检查一遍语法错误，能在报错发生前就拦截一部分问题，减少无谓的
生成-报错-修复往返。这个可以作为你后续打磨的方向，不必现在就做。
