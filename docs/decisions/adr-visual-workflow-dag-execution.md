# ADR: 视觉工作流采用确定性拓扑批次执行计划

## 状态

Accepted

## 日期

2026-08-19

## 背景

视觉工作流把图片、提示词和视频模型连接成用户可保存的有向图。后续节点可能触发耗时且计费的异步供应商任务，因此在真正提交模型任务前，必须先证明固定修订版本是可执行的 DAG，并且分支可以安全并行。

## 决策

后端使用 Python 标准库 `graphlib.TopologicalSorter` 生成确定性的拓扑批次：

- 节点顺序以工作流文档中的顺序作为稳定 tie-breaker，不依赖字典遍历偶然顺序。
- 请求运行目标时，只编译目标节点及其祖先闭包，避免调度无关分支。
- 端口、节点版本、重复连接和环路先由权威校验器拒绝；编译器不向供应商发请求。
- 当前公开 `compile` API 与 `dry-run` Run API；`execute` 明确返回 `EXECUTION_NOT_AVAILABLE`，直到真实适配器、成本护栏和状态恢复完成。
- Run 使用可选 `clientRequestId` 唯一约束实现重试幂等，重复提交返回同一 Run。

## 被否决的方案

### 直接在 API 请求中递归执行节点

被否决：会把长任务绑定到 HTTP 生命周期，也无法可靠恢复、取消或重放事件。

### 立即引入 Celery/Redis/外部工作流框架

被否决：当前单机 Python 后端已有 SQLite 和 asyncio 基础；在完成契约、状态机和供应商适配前引入分布式调度会扩大运维与故障面。

### 允许 execute 默认开启

被否决：工作流节点可能对应付费模型。必须先完成运行前校验、并发限制、缓存和审计，再开放真实提交。

## 后果

正面：编译结果可测试、可缓存、可在 SSE/轮询层复用；分叉天然支持并行，局部运行不会误跑无关节点。

代价：当前 Run 只保存 `PLANNED` 计划，不能产生模型结果；后续需要补充 NodeRun 状态机、事件序列、缓存和供应商适配器。
