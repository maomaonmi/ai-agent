# 全能模式：项目化多模态对话工作区计划书

## 1. 文档目的

本文定义“全能模式”的产品体验、领域模型、前后端架构、现有能力适配方式、分阶段实施计划与验收标准。

全能模式不是把研究、写作、PPT、生图、视频几个独立页面简单组合起来，而是建立一个统一的多模态对话空间：用户可以在同一条自然对话中持续生成、查看、引用和修改不同类型的作品，并可随时把普通会话加入项目，形成长期可维护的创作空间。

本文覆盖完整目标架构，但实施必须按阶段推进。第一阶段只验证最关键的纵向闭环：

> 全能对话 → 生成作品卡片 → 点击滑出右侧面板 → 刷新后恢复 → 会话加入项目

---

## 2. 问题陈述

### 2.1 How Might We

如何让用户在保持自然聊天体验的同时，连续完成研究、写作、论文、PPT、生图和视频等跨模态任务，并确保任意历史消息都能准确打开当时生成的作品版本，而不会因模式切换、最新结果覆盖或多个工作区共存而发生内容串台？

### 2.2 当前产品问题

现有项目已经具备完整或接近完整的独立能力：

- 深度研究已有聊天区与右侧报告面板；
- AI 写作已有结构化草稿、正文、论文大纲和排版工作台；
- 图片已有生图工作室、批次历史和候选图；
- 视频已有生成任务、实时进度、参考素材和历史任务；
- PPT 已有模板市场、生成 Run、Presentation 和专业编辑工作台；
- `ai-input` 原型已有全能入口、生图、视频、PPT、研究等视觉素材和输入形态。

但这些能力目前采用不同的状态和导航模式：

- 部分能力由会话 `mode` 决定页面；
- 部分能力由全屏 `view` 切换；
- PPT 使用独立路由；
- 图片和视频主要读取各自全局历史；
- 写作数据直接扩展在 `SessionSnapshot` 上；
- 研究报告以消息索引驱动右侧面板；
- `ChatInterface.tsx` 已集中承担大量互不相同的模式状态。

如果继续通过 `mode === xxx` 决定右侧展示内容，同一会话中先后生成图片、文章、视频和 PPT 时必然出现状态覆盖和内容串台。

## 3. 产品定义

### 3.1 一句话定义

全能模式是一个对话优先、项目可选、作品驱动的跨模态创作空间。

### 3.2 核心原则

1. **对话优先**：用户可以直接说需求，不必先理解或选择复杂工作流。
2. **项目可选**：普通会话可独立存在，也可随时加入项目。
3. **作品驱动**：右侧面板展示用户选中的作品，不由会话模式决定。
4. **版本精确**：历史消息打开该消息生成或引用的具体版本，而不是无条件打开最新版。
5. **显式引用**：AI 可以使用上下文理解“它”，但必须在输入区向用户显示实际引用对象。
6. **专业能力保留**：研究、写作、图片、视频、PPT 等独立入口继续存在。
7. **同一实体复用**：全能面板与专业工作台操作同一份作品，不能复制出互不关联的数据。

### 3.3 产品结构

```text
项目 Project（可选）
└── 会话 Conversation
    ├── 消息 Message
    ├── 消息作品引用 MessageArtifactLink
    └── 作品 Artifact
        ├── 版本 ArtifactVersion
        ├── 素材 Asset
        └── 派生关系 ArtifactRelation
```

### 3.4 普通聊天与项目空间的关系

- 新会话默认不属于任何项目，`projectId = null`；
- 用户可在聊天中途将整条会话加入现有项目或新建项目；
- 加入项目时，会话中的作品一并进入项目，不复制数据；
- 一个项目可以包含多条会话；
- 一条会话同一时间只直接归属一个项目；
- 左侧项目树只展示项目内会话，不混入图片、视频、文章或 PPT；
- 项目作品通过项目页或会话中的作品入口统一查看。

## 4. 已确认的产品决策

### 4.1 项目上下文

- 同一项目内允许跨会话检索；
- 模型默认只自动注入项目级摘要和作品摘要；
- 真正使用某个具体作品前，前端必须显示引用；
- 不默认把其他会话的完整正文、图片或大文件全部注入模型上下文。

### 4.2 跨项目引用

- 允许引用其他项目中的作品；
- 作品仍归属原项目；
- UI 显示“来自其他项目”；
- 不静默复制作品；
- 若未来需要复制，必须作为用户明确发起的独立操作。

### 4.3 历史版本

- 点击历史消息中的作品卡片，默认打开该消息对应的历史版本；
- 如果该版本不是当前最新版，面板明确提示“这不是最新版本”；
- 提供“查看最新版”操作；
- 历史版本默认只读；修改历史版本时创建新版本或分支，不能覆盖历史。

### 4.4 能力选择

- 自然语言默认由 AI 自动判断需要调用的能力；
- 输入栏中的“图片、视频、写作、研究、PPT”等按钮只影响本轮请求；
- 按钮是能力提示或强制路由，不是永久切换整个会话模式；
- 输入栏同时提供“联网搜索”和“深度思考”两个独立开关；
- 联网搜索与深度思考不是互斥模式，可以单独开启，也可以同时开启；
- 两个开关复用现有 `webSearch`、`deepThinking`、RuntimeSettings、参数持久化和 SSE 节点反馈链路，不另建一套执行系统；
- 开关状态作为会话级运行偏好保留，同时在每次请求的 `TurnContext` 中冻结本轮实际值，保证历史可解释和重试一致；
- 请求完成后仍停留在同一全能会话。

### 4.5 右侧面板

- 进入会话时右侧默认关闭，不自动恢复或打开作品；
- 用户点击消息中的作品或文件卡片后，面板从右侧滑出；
- 右上角提供关闭、最大化、恢复分栏和更多操作；
- 面板已打开时点击其他作品，原地切换内容，不重复关闭和滑出；
- 关闭面板时清除当前隐式活动作品，避免不可见对象继续被“它”引用。

## 5. 用户体验设计

### 5.1 左侧栏

左侧栏增加项目区域：

```text
更多

项目
[ 新建项目 ]

▾ 新能源发布
   市场研究
   宣传创意
   汇报材料

▸ 毕业论文

历史会话
   普通聊天 A
   普通聊天 B
```

约束：

- 项目节点下只展示会话；
- 项目支持展开、收起、重命名和删除；
- 会话支持加入项目、移动项目和移出项目；
- 删除项目时必须区分“仅删除项目容器”和“同时删除其中会话”，默认采用可恢复或安全选项；
- 第一阶段可以不做复杂项目首页，但数据模型必须支持后续扩展。

### 5.2 将会话加入项目

入口：

- 会话顶部标题菜单；
- 左侧会话更多菜单；
- 当会话已产生多个作品时，可出现一次非阻塞式整理提示。

确认弹窗示例：

```text
将此对话加入“新能源汽车发布”？

将一并归入：
• 18 条消息
• 1 份研究报告
• 4 张图片
• 1 个视频任务

[取消] [确认加入]
```

加入动作应为归属关系更新，不应重新创建消息或复制作品。

### 5.3 全能输入区

全能输入区直接沿用 `ai-input` 原型的核心构图：上半部分是宽大的自然语言输入面，下半部分只有一条连续工具栏。不能把“创作能力”和“运行能力”各自拆成新的一行，否则输入框会变成参数面板，破坏自然聊天的主次关系。

桌面端结构：

```text
┌──────────────────────────────────────────────────────────────────────────────┐
│ 发消息或按住空格说话……                                            · ·     │
│                                                                              │
│ [+] [全能对话›] [PPT] [音乐] [写作] [生图] [视频] [研究] [更多]  │ [联网] [深思] [模型›] [发送] │
└──────────────────────────────────────────────────────────────────────────────┘
```

工具栏分为四个语义组，但视觉上仍保持同一行：

1. **附件入口**：最左侧独立的 `+`；
2. **创作能力入口**：全能对话、PPT、音乐、写作、生图、视频、研究、更多；
3. **运行增强开关**：联网搜索、深度思考；
4. **模型与发送区**：模型快捷切换、语音/发送按钮。

创作能力入口使用原型中的图标加文字样式。“全能对话”是默认高亮状态；点击 PPT、写作、生图、视频或研究，只为本轮添加能力标签和相应参数，不离开当前全能会话。工具栏中的“全能对话›”可以展开对话相关选项，但联网搜索和深度思考不能藏在该单选菜单中，因为它们允许同时启用。

“联网搜索”和“深度思考”放在创作入口之后、模型入口之前，以轻量紧凑按钮呈现。它们属于运行增强项，在视觉上通过一个弱分隔符与左侧创作入口区分，但不能另起一行：

```text
关闭：[🌐 联网] [🧠 深思]
开启：[🌐 联网 ✓] [🧠 深思 ✓]
```

交互要求：

- 点击任一开关只改变该能力，不关闭另一个开关；
- 开启状态必须通过颜色、图标和文字共同表达，不能只依赖颜色；
- 桌面端显示紧凑文字“联网”“深思”，悬停或聚焦时解释完整含义；
- 联网搜索的高级参数继续复用现有搜索选项入口；
- 深度思考继续复用现有推理链路和状态反馈；
- 两者同时开启时，执行链路允许先深度分析信息需求、按需联网检索，再综合推理；具体节点顺序由现有后端能力编排决定；
- 在不支持某项能力的模型下，按钮应禁用并解释原因，不能点击后静默降级；
- 流式执行过程中锁定本轮实际配置，用户对开关的后续修改只影响下一轮请求。

响应式收纳优先级：

- 宽屏完整显示图标和文字；
- 中等宽度先缩短“联网搜索/深度思考”为“联网/深思”，再隐藏低优先级能力文字，仅保留图标和 Tooltip；
- 更窄时将音乐及低频能力收入“更多”，但始终保留附件、全能对话、联网、深思、模型和发送；
- 移动端不强行横向塞满所有按钮，采用首要操作栏加“更多”底部抽屉；
- 不允许工具栏自然换成两行，以免输入框高度和消息区位置在能力切换时跳动。

当系统或用户选中了引用对象时，在输入框上方显示：

```text
正在引用：@新春海报 · 图片 ×
```

能力参数以本轮动态参数条展示，例如：

```text
[AI 生视频 ×] [万相 2.7] [16:9] [10 秒] [参考：@新春海报]
```

输入提交时形成明确的 `TurnContext`，提交完成后清理本轮能力提示；作品引用是否保留应以当前右侧活动作品和用户操作为准。

引用标签和动态参数条属于输入内容区内部、正文输入面的下缘辅助区域；它们不是第二条常驻工具栏。没有引用或专属参数时完全不占空间。

### 5.4 对话流中的作品卡片

所有生成型能力采用统一外壳，不把完整专业工作台直接塞入聊天流。

统一卡片信息：

- 作品类型和标题；
- 缩略预览；
- 生成状态；
- 当前消息对应版本；
- 主要动作；
- 跨项目来源提示；
- 派生来源提示。

示例：

```text
┌──────────────────────────────┐
│ 🖼 新春电商主视觉             │
│ 4 张图片 · 已完成 · 版本 2    │
│ [缩略图] [缩略图] [缩略图]    │
│ 查看作品  继续编辑  用于视频  │
└──────────────────────────────┘
```

实时任务卡片由任务事件更新，不通过插入新消息模拟进度。

### 5.5 右侧作品面板

面板状态：

```ts
type WorkspacePanelState =
  | { status: 'closed' }
  | {
      status: 'opening' | 'open';
      artifactId: string;
      versionId: string;
      displayMode: 'split' | 'maximized';
    };
```

面板顶部统一提供：

- 作品类型、标题和状态；
- 历史版本提示；
- “查看最新版”；
- 版本入口；
- 最大化或恢复分栏；
- 关闭；
- 进入专业工作台。

面板内容由作品类型适配器决定，不由当前聊天模式决定。

### 5.6 “它”的指代规则

指代解析优先级：

1. 用户在本轮显式 `@` 的作品；
2. 用户本轮附加的文件或素材；
3. 当前右侧活动作品；
4. 当前会话最近一次相关作品；
5. 项目检索出的候选摘要；
6. 仍有多个合理候选时请求用户选择。

系统把当前右侧作品理解为“它”时，输入区必须显示对应引用标签。右侧关闭后自动清除这项隐式引用。

## 6. 统一领域模型

### 6.1 Project

```ts
interface Project {
  id: string;
  name: string;
  description?: string;
  summary?: string;
  createdAt: string;
  updatedAt: string;
  archivedAt?: string;
}
```

### 6.2 Conversation

```ts
interface Conversation {
  id: string;
  projectId: string | null;
  title: string;
  mode: 'omni' | ExistingMode;
  createdAt: string;
  updatedAt: string;
}
```

`mode` 仍用于表达会话的主要执行体验，但不能再决定右侧具体展示哪一类作品。

### 6.3 Artifact

```ts
type ArtifactKind =
  | 'image'
  | 'video'
  | 'document'
  | 'thesis'
  | 'research_report'
  | 'presentation';

interface Artifact {
  id: string;
  projectId: string | null;
  originConversationId: string;
  kind: ArtifactKind;
  title: string;
  summary: string;
  status: 'draft' | 'queued' | 'generating' | 'ready' | 'failed' | 'archived';
  currentVersionId: string;
  metadata: Record<string, unknown>;
  createdAt: string;
  updatedAt: string;
}
```

`metadata` 只保存类型专属索引和轻量信息，不能成为无限扩张的任意对象垃圾场。各类型的正式内容由类型专属表或现有领域实体管理。

### 6.4 ArtifactVersion

```ts
interface ArtifactVersion {
  id: string;
  artifactId: string;
  versionNumber: number;
  parentVersionId?: string;
  status: 'draft' | 'generating' | 'ready' | 'failed';
  sourceRef: ArtifactSourceRef;
  summary: string;
  createdByMessageId?: string;
  createdAt: string;
}
```

`sourceRef` 指向现有类型实体，例如：

- 图片：`imageBatchId + imageAssetIds`；
- 视频：`videoTaskId`；
- 写作：结构化文档快照或文档 revision；
- 研究：报告消息或独立 report revision；
- PPT：`presentationId + revision + runId`。

### 6.5 MessageArtifactLink

```ts
interface MessageArtifactLink {
  id: string;
  conversationId: string;
  messageId: string;
  artifactId: string;
  versionId: string;
  relation: 'created' | 'updated' | 'referenced' | 'derived';
  displayOrder: number;
  createdAt: string;
}
```

这是防止右侧串台的核心记录。消息卡片只能通过该关系打开作品，不允许通过“最新生成结果”或类型全局状态猜测目标。

### 6.6 ArtifactRelation

```ts
interface ArtifactRelation {
  id: string;
  sourceArtifactId: string;
  sourceVersionId?: string;
  targetArtifactId: string;
  targetVersionId?: string;
  relation: 'derived_from' | 'uses_as_reference' | 'converted_from';
  createdAt: string;
}
```

用于表达“研究报告生成 PPT”“图片作为视频首帧”“文章由研究报告扩写”等来源关系。

### 6.7 TurnContext

```ts
interface TurnContext {
  preferredCapability?: ArtifactKind | 'auto';
  runtimeCapabilities: {
    webSearch: 'off' | 'auto' | 'on';
    deepThinking: 'off' | 'auto' | 'on';
  };
  activeArtifact?: { artifactId: string; versionId: string };
  mentionedArtifacts: Array<{ artifactId: string; versionId?: string }>;
  attachments: ChatAttachment[];
  projectSummary?: string;
  candidateArtifactSummaries?: ArtifactSummary[];
}
```

服务端必须对客户端传来的项目与作品引用做权限和归属校验，不能只信任 ID。

## 7. 前端架构

### 7.1 新增边界

建议把全能模式从当前超大 `ChatInterface.tsx` 中拆出以下边界：

```text
features/omni/
├── OmniConversationShell.tsx
├── OmniComposer.tsx
├── OmniCapabilityBar.tsx
├── ArtifactMessageCard.tsx
├── ArtifactPanel.tsx
├── ArtifactPanelHeader.tsx
├── ArtifactRenderer.tsx
├── artifactAdapters/
│   ├── imageAdapter.tsx
│   ├── videoAdapter.tsx
│   ├── writingAdapter.tsx
│   ├── researchAdapter.tsx
│   └── pptAdapter.tsx
├── store.ts
└── types.ts

features/projects/
├── ProjectSidebarSection.tsx
├── CreateProjectDialog.tsx
├── MoveConversationDialog.tsx
├── ProjectConversationTree.tsx
└── store.ts
```

### 7.2 前端状态分层

必须区分：

- **持久领域状态**：项目、会话、作品、版本、消息关系；
- **可恢复界面状态**：面板开关、最大化状态、滚动位置；
- **本轮临时状态**：能力提示、输入引用、附件；
- **实时任务状态**：图片、视频、PPT、研究生成进度。

首期不建议把所有服务端领域实体完整复制到一个巨型 Zustand Store。使用查询缓存/局部 store 管理实体索引，实时任务单独订阅。

### 7.3 作品适配器

```ts
interface ArtifactAdapter<TSummary = unknown> {
  kind: ArtifactKind;
  renderMessageCard(props: ArtifactCardProps<TSummary>): React.ReactNode;
  renderPanel(props: ArtifactPanelProps): React.ReactNode;
  getContextSummary(artifact: Artifact): string;
  getActions(artifact: Artifact, version: ArtifactVersion): ArtifactAction[];
  getProfessionalWorkspaceUrl?(artifact: Artifact): string;
}
```

适配器统一的是外壳和行为契约，不强迫图片、视频、文档、PPT 使用完全相同的内部状态结构。

### 7.4 `ai-input` 原型的使用方式

可复用：

- 欢迎区视觉；
- 底部能力快捷按钮；
- 图片广场素材；
- PPT 模板封面素材；
- 视频参数面板视觉；
- 研究推荐问题和卡片视觉。

不可直接照搬：

- 通过单一 `mode` 条件渲染整个页面；
- 点击能力后离开统一对话；
- 仅用组件局部状态保存生成结果；
- 把能力按钮当作长期会话模式。

素材可以迁入主 Next.js 前端的 `public` 目录并统一命名，但实施时需先检查重名和引用路径。

## 8. 现有能力适配

### 8.1 深度研究

现状最接近统一作品模型，可优先适配：

- 将报告从“仅靠消息索引选择”升级为明确 `artifactId/versionId`；
- 保留消息中的研究链路和来源；
- `ResearchWorkspace` 改为接收受控报告版本；
- 研究插图更新产生新的报告版本或版本附属资源状态；
- 旧会话可通过迁移适配器按需生成 Artifact 记录。

### 8.2 AI 写作和论文

- 保留现有 `WritingDraft`、`WritingDocumentState`、`ThesisOutlineState`；
- 将其包装为 document/thesis Artifact 的版本内容；
- `WritingWorkspace` 支持嵌入右侧面板和专业全屏两种容器；
- 自动保存时更新当前文档 revision，不把整个写作状态继续无限扩展到通用 SessionSnapshot；
- 进入专业工作台后继续编辑同一 Artifact。

### 8.3 图片

- `ImageBatch` 映射为一个图片作品版本；
- 批次中的多张候选图作为版本内 Asset；
- 明确区分“作品”“生成批次”“候选图”；
- `ImageStudioWorkspace` 改为接受 `artifactId/versionId`，不能依赖全局历史决定当前内容；
- 对历史图片的编辑创建新版本，并记录参考关系。

### 8.4 视频

- `VideoTask` 映射为视频作品版本；
- 任务状态通过统一事件通道更新作品卡片和右侧面板；
- 图片首帧、尾帧、参考视频等写入 ArtifactRelation 或版本输入清单；
- `VideoStudioWorkspace` 支持打开指定任务，而不是默认展示全局最新任务；
- 失败重试应产生新的任务尝试，并保留版本链路。

### 8.5 PPT

- `presentationId` 对应 Artifact；
- Presentation revision 对应 ArtifactVersion 或与之建立稳定映射；
- `runId` 是生成任务，不是作品身份；
- 右侧面板提供轻量预览；
- “进入 PPT 工作台”打开现有专业路由，但操作同一 presentation；
- 返回全能会话后，消息卡片和右侧面板可看到新版本。

## 9. 后端与存储设计

### 9.1 建议新增表

```text
projects
project_conversations
artifacts
artifact_versions
message_artifact_links
artifact_relations
artifact_assets（若现有素材表不能统一索引）
```

如果一条会话只能属于一个项目，可直接在 sessions 增加 nullable `project_id`；若未来需要快捷方式、多项目收藏或共享视图，再引入关联表。第一阶段优先采用单归属，降低复杂度。

### 9.2 API 边界

项目：

```text
POST   /api/projects
GET    /api/projects
PATCH  /api/projects/{projectId}
DELETE /api/projects/{projectId}
POST   /api/projects/{projectId}/conversations/{conversationId}
DELETE /api/projects/{projectId}/conversations/{conversationId}
```

作品：

```text
GET  /api/conversations/{conversationId}/artifacts
GET  /api/artifacts/{artifactId}
GET  /api/artifacts/{artifactId}/versions
GET  /api/artifacts/{artifactId}/versions/{versionId}
POST /api/artifacts/{artifactId}/derive
```

全能对话：

```text
POST /api/omni/chat
GET  /api/omni/chat/{runId}/events
```

首期可以继续复用现有 SSE 机制，但统一事件信封：

```ts
type OmniEvent =
  | { type: 'assistant.delta'; messageId: string; delta: string }
  | { type: 'artifact.created'; artifact: Artifact; version: ArtifactVersion }
  | { type: 'artifact.progress'; artifactId: string; versionId: string; progress: number; phase: string }
  | { type: 'artifact.ready'; artifactId: string; versionId: string }
  | { type: 'artifact.failed'; artifactId: string; versionId: string; error: ApiError }
  | { type: 'message.artifact_linked'; link: MessageArtifactLink }
  | { type: 'run.done'; usage?: TokenUsage };
```

事件必须携带 `artifactId + versionId`，不能只携带类型或“当前任务”。

### 9.3 事务要求

以下操作需要原子性或可靠补偿：

- 创建作品、首个版本和消息关系；
- 将会话加入项目并更新会话内无项目作品的归属；
- 生成完成后更新版本和作品 currentVersion；
- 从历史版本创建新版本；
- PPT 专业工作台保存 revision 后同步 ArtifactVersion。

不能出现“文件已经生成，但聊天中永久找不到”的孤儿结果。任务恢复流程应能根据 provider task/run ID 补建或修复关联。

## 10. AI 路由、记忆与上下文

### 10.1 能力路由

路由输入：

- 用户文本；
- 本轮能力提示；
- 本轮冻结的联网搜索与深度思考配置；
- 显式和隐式作品引用；
- 附件类型；
- 当前项目摘要；
- 可用模型与能力；
- 用户是否请求修改既有作品。

路由输出至少包含：

```ts
interface OmniRouteDecision {
  capability: 'chat' | ArtifactKind;
  operation: 'create' | 'revise' | 'derive' | 'explain';
  targetArtifactId?: string;
  targetVersionId?: string;
  referenceArtifacts: Array<{ artifactId: string; versionId?: string }>;
  confidence: number;
  needsClarification: boolean;
}
```

用户明确点击能力按钮时优先服从用户意图；但如果输入与能力完全冲突，应提示而不是静默执行错误任务。

联网搜索和深度思考属于横向运行能力，不属于 `capability` 的互斥取值。无论本轮最终路由到普通回答、研究、写作、PPT、生图或视频，都可以在对应链路支持的范围内携带这两个开关。首期直接把现有 `RuntimeSettings.webSearch` 与 `RuntimeSettings.deepThinking` 透传给全能请求，避免重复实现搜索、推理、节点进度与持久化逻辑。

### 10.2 记忆分层

1. 会话消息摘要；
2. 项目摘要；
3. 作品目录摘要；
4. 作品版本摘要；
5. 本轮明确引用的具体内容；
6. 必要时按需读取的源文件或结构化数据。

项目自动检索只能把候选摘要交给模型。模型决定使用具体作品后，前端/服务端应产生可见引用记录。

### 10.3 跨项目安全

- 跨项目检索默认不自动扫描所有项目正文；
- 用户明确搜索或引用时才查询；
- 引用卡片显示来源项目；
- 服务端校验当前用户对源项目和作品的访问权限；
- 删除或归档源项目时，保留可解释的引用状态并避免目标作品静默损坏。

## 11. 分阶段实施计划

### 阶段 0：契约冻结与拆分准备

目标：在不改变现有用户行为的前提下建立统一语言。

任务：

- 定义 Project、Artifact、ArtifactVersion、MessageArtifactLink、TurnContext；
- 为消息补充稳定 `messageId`，停止依赖数组索引作为长期身份；
- 定义统一 OmniEvent；
- 建立 ArtifactAdapter 注册机制；
- 给 `ChatInterface.tsx` 划出全能模式和右侧面板边界；
- 建立数据库迁移和回滚方案；
- 为现有能力建立 ID 映射表。

退出标准：契约测试通过，旧模式无行为回归。

### 阶段 1：纵向闭环 MVP

目标：证明统一作品链路真实可用。

范围：

- 左侧新建项目和项目会话树；
- 新建全能会话；
- 全能输入框提供可同时开启的联网搜索与深度思考开关；
- 复用现有 RuntimeSettings 和请求 meta 透传链路；
- 普通会话加入、移动、移出项目；
- 至少接入文本/文档和图片两种差异明显的作品；
- 生成完成后在消息中插入统一作品卡片；
- 点击卡片按 `artifactId + versionId` 滑出右侧面板；
- 关闭、最大化和切换作品；
- 历史版本提示和“查看最新版”；
- 当前活动作品作为“它”的隐式引用，并在输入区显式显示；
- 页面刷新后恢复消息、作品、版本和项目归属，但面板默认保持关闭。

退出标准：完整验收链路端到端通过，不依赖模拟数据。

### 阶段 2：五类作品全面接入

目标：将研究、写作/论文、图片、视频、PPT 全部纳入统一工作区。

任务：

- 逐一实现五类 ArtifactAdapter；
- 视频、PPT、研究任务接入统一实时事件；
- 专业工作台与全能面板共享实体；
- 支持作品派生：研究→写作、写作→PPT、图片→视频等；
- 支持显式 `@作品`；
- 支持跨会话项目摘要检索；
- 统一错误、重试和取消行为。

### 阶段 3：项目级智能与跨项目引用

目标：让项目成为真正的长期创作记忆空间。

任务：

- 项目摘要增量更新；
- 项目作品目录和搜索；
- 跨会话候选召回；
- 跨项目显式引用及来源提示；
- 项目页的会话与作品概览；
- 作品关系视图或来源链路；
- 项目归档、删除和引用完整性策略。

### 阶段 4：迁移与体验完善

目标：处理旧数据并提升可用性。

任务：

- 旧研究、写作、图片、视频、PPT 历史按需迁移为 Artifact；
- 空状态、加载、失败、断线恢复和长任务体验；
- 移动端采用全屏抽屉，不强行左右分栏；
- 性能优化、虚拟化、缩略图和资源懒加载；
- 可访问性、键盘操作和焦点管理；
- 埋点和可观测性。

## 13. 验收标准

### 13.1 项目

- 用户可以在左侧新建项目；
- 项目下只显示会话；
- 未归属会话可随时加入项目；
- 加入项目后消息和作品不丢失、不复制；
- 会话可移动到其他项目或移出项目；
- 刷新后项目树和归属保持一致。

### 13.2 全能对话

- 用户无需切换页面即可完成至少两类作品生成；
- 能力按钮只影响本轮请求；
- 联网搜索和深度思考都可独立开启、关闭；
- 联网搜索与深度思考可同时开启，且任一按钮的操作不会重置另一个按钮；
- 请求执行过程中使用提交时冻结的开关配置；
- 开关状态、搜索高级参数、请求 meta 和节点进度复用现有完整链路；
- 模型不支持相应能力时给出明确禁用或降级说明；
- AI 自动路由结果在 UI 中可见且可解释；
- 文本回答与作品卡片可以出现在同一对话流中。

### 13.3 右侧面板

- 新进入会话时面板关闭；
- 点击任意作品卡片打开精确作品和版本；
- 点击另一作品时面板原地切换且无串台；
- 点击历史消息打开历史版本；
- 历史版本明确提示并可切换最新版；
- 关闭面板后清除隐式活动作品；
- 最大化和恢复分栏不丢失编辑或查看状态。

### 13.4 AI 引用

- 右侧活动作品可被“它”解析；
- 输入区显示实际引用标签；
- 显式 `@` 优先于隐式活动作品；
- 多个合理候选时不会静默选择错误对象；
- 项目自动检索只注入摘要；
- 跨项目引用显示来源项目且不复制作品。

### 13.5 稳定性

- 任务事件重复或乱序不会生成重复卡片；
- 刷新和断线后可恢复真实任务状态；
- 同一会话存在多种作品时不会互相覆盖；
- 专业工作台修改后，全能会话可看到同一作品的新版本；
- 生成文件成功但消息关系失败时有补偿或恢复机制。

## 14. 风险与应对

### 14.1 `ChatInterface.tsx` 继续膨胀

风险：所有全能逻辑继续堆入单组件会使状态耦合进一步恶化。

应对：第一阶段先建立 Omni Shell、Composer、Artifact Panel 和 Adapter 边界，再接能力。

### 14.2 旧能力身份不统一

风险：ImageBatch、VideoTask、WritingDocument、Research Message、Presentation 的 ID 语义不同。

应对：Artifact 作为统一身份，`sourceRef` 适配现有实体，不强行立即重写所有领域表。

### 14.3 SessionSnapshot 无限扩张

风险：继续把每种作品完整状态塞入快照会导致读写、迁移和恢复越来越脆弱。

应对：快照只保存会话 UI 所需轻量状态；作品内容独立持久化，通过 ID 查询。

### 14.4 实时事件串台

风险：并行图片、视频、PPT 任务仅靠“当前任务”状态更新错误卡片。

应对：所有事件携带 runId、artifactId、versionId，客户端按实体归并并保证幂等。

### 14.5 项目自动上下文过量

风险：同一项目积累大量作品后，上下文成本和误引用增加。

应对：项目摘要 + 候选检索 + 显式读取三段式注入，不默认加载全文。

### 14.6 历史版本被意外覆盖

风险：从旧消息进入编辑后直接修改旧版本，破坏历史真实性。

应对：历史版本只读；修改产生新版本，保留 parentVersionId 和消息关系。

### 14.7 专业模式与全能模式双写

风险：同一 PPT 或文章在两个入口分别保存，产生分叉数据。

应对：专业工作台必须接受并操作 Artifact 映射的现有实体；ArtifactVersion 同步由服务层统一完成。

## 15. 关键假设与验证

### 15.1 必须成立

- 用户能理解“对话中生成作品，点击后右侧打开”的交互；
- 现有五类能力可以通过适配器受控打开指定实体；
- 消息、作品、版本能形成稳定且可恢复的关系；
- 任务 provider 能提供足够稳定的任务 ID 用于断线恢复。

验证方式：阶段 1 使用文档 + 图片完成真实端到端测试，并进行刷新、历史版本和并行任务测试。

### 15.2 应当成立

- 用户愿意在需要长期整理时主动创建项目；
- 当前右侧作品作为“它”的默认对象符合用户预期；
- 能力按钮作为本轮提示比永久模式切换更自然；
- 项目摘要足以支持大部分跨会话召回。

验证方式：记录项目创建时机、引用标签移除率、路由纠正率和跨会话检索成功率。

### 15.3 可能成立

- 用户未来需要作品关系图；
- 用户需要多人协作项目；
- 用户需要一个作品同时正式归属多个项目；
- 用户需要多作品并排编辑。

这些不进入首期范围。

---

## 16. 暂不实施

- 多个作品同时并排预览或编辑——首期只维护一个活动面板，避免焦点和指代复杂化；
- 自由画布和作品连线——先验证自然对话与作品面板；
- 一条会话同时归属多个项目——先采用单项目归属；
- 静默复制跨项目作品——会破坏来源和版本关系；
- 自动把项目所有内容加入模型上下文——成本高且容易误引用；
- 一次性重写全部专业工作台——使用适配器渐进接入；
- 将所有生成参数永久显示在输入栏——参数按本轮能力动态显露；
- 把联网搜索和深度思考重新实现为新的互斥模式——直接复用现有两条可组合能力链路；
- 默认打开上次查看作品——已确认进入会话时右侧保持关闭；
- 用最新版本覆盖历史消息指向——历史消息必须忠实指向当时版本；
- 首期多人协作、权限矩阵和公开分享——待单用户作品模型稳定后再设计。

## 17. 成功指标

第一阶段不以“接入能力数量”作为唯一成功标准，重点观察：

- 作品卡片打开正确率；
- 历史版本定位正确率；
- 刷新恢复成功率；
- 生成结果孤儿率；
- 用户纠正“它”所指对象的比例；
- 全能模式下完成跨类型连续任务的成功率；
- 会话加入项目后的数据一致性；
- 旧模式回归数量；
- 从全能面板进入专业工作台后版本同步成功率。

建议技术底线：

- 消息—作品—版本错误绑定为 0；
- 成功生成但无法从会话恢复的作品为 0；
- 项目移动不产生重复消息或重复作品；
- 所有实时事件处理具备幂等性。

---

## 18. 推荐实施顺序

1. 冻结领域契约和事件信封；
2. 给消息增加稳定 ID；
3. 建立 Project 与 Artifact 持久化；
4. 建立右侧面板状态机和统一卡片；
5. 将联网搜索与深度思考的现有 RuntimeSettings 链路接入全能输入框，并验证同时开启；
6. 接入一个文档型作品；
7. 接入图片型作品；
8. 完成项目加入与刷新恢复闭环；
9. 验证历史版本、“它”的引用和并行任务；
10. 接入研究、写作/论文、视频和 PPT；
11. 最后启用项目级检索与跨项目引用。

在步骤 1—8 未稳定前，不应同时全面改造五类专业工作台。

---

## 19. 最终推荐方向

采用“对话优先、项目可选、作品驱动、版本精确”的作品工作台方案。

前端表面保持自然聊天：用户直接表达目标，通过轻量能力按钮影响本轮请求，生成结果以统一作品卡片进入对话。用户点击卡片后，右侧按需滑出对应作品的指定版本；关闭面板后回到完整聊天。左侧项目只组织会话，不把不同媒体文件混入导航树。

底层则使用 Project、Conversation、Artifact、ArtifactVersion 和 MessageArtifactLink 建立可靠关系。项目负责长期组织和跨会话摘要记忆；全能模式负责任务编排与自然对话；右侧作品面板负责查看和编辑；专业模式继续保留，并操作同一作品实体。

这一方案能够最大限度复用现有研究、写作、图片、视频和 PPT 基础，同时从根源上解决右侧面板内容冲突、历史版本失真和跨模态上下文丢失问题。
